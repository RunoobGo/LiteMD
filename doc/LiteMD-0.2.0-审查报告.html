结构评价

  • Go 侧分层标准：internal/ 按领域分包（config/fileio），binding 层（app.go）不掺业务逻辑、错误带哨兵值供前端 errors.Is 分流——教科书式 Wails 项目布局
  • 前端模块边界清晰：titlebar.ts 通过依赖注入接收窗口操作、测试零依赖运行；file-ops.ts 统一 mock/真实 binding 的切换点，设计有想法
  • 复杂度右对齐：无框架、无状态库、无 DI 容器——对单机编辑器是正确的克制，没有过度设计
  • main.ts 641 行偏胖：主题、快捷键、标签渲染、图片拖入、启动流程全在一个文件；目前尚可维护，但再加 2 个功能就该拆（如 theme.ts / shortcuts.ts）
  • build/ 与 build_darwin/ 双真相源：两处 Info.dev.plist 内容已漂移（见缺陷 #7），Wails 实际读取 build/，macOS 构建配置存在用错文件的风险
  • 源码分发包含 .git（2.3MB）与 node_modules：2.9MB 包体中约 90% 是冗余，且含平台特定二进制；建议改用 git archive 或补 .gitignore 导出规则

03架构与后端代码质量

✅ 亮点（值得肯定的设计）

原子写实现完整且解释了「为什么」internal/fileio/fileio.go:90-124

临时文件 → Sync() → Rename() 三段式，并在注释中明确说明了缺失 Sync 时「rename 元数据可能先于数据持久化，掉电后目标文件长度正确但内容为空」的根因。config.go 的 Save 采用同源实现。这是很多生产项目都会写错的细节。

读取路径的防御纵深完整internal/fileio/fileio.go:47-82

IsRegular 拒绝 FIFO/设备（防 /dev/zero OOM 与 FIFO 挂起）→ 50MB 上限 → LimitReader 兜底（防 Stat 后文件被替换的 TOCTOU）→ BOM 剥除 → UTF-8 校验。每层守卫都对应一类真实故障模式。

并发时序处理成熟app.go:35-70 / startupfile.go:58-83

ctx 读写锁保护 + pendingNotify CAS 补发机制，正确处理了「二实例回调先于 startup 钩子到达」的竞态；startupFileQueue 的生产者-消费者模型有并发测试覆盖（8 生产者 × 50 条）。

ReDoS 防护有量化证据frontend/src/obsidian.ts:21-36 / latex.ts:69-93

WIKI_RE 用字符类排除 + 有界量词替代惰性匹配，注释给出实测数据（8000 个 [ 输入：191ms → <1ms）；围栏扫描改按行状态机 O(n)。测试中还有「大输入 < 500ms」的回归守卫断言。

后端缺陷

🔴 #2保存期间的并发输入会被回滚（数据丢失路径）frontend/src/main.ts:487-489 → tabs.ts:139-151

handleSave 先取 editor.getContent() 快照，await saveFile(...) 的 IO 窗口期内用户继续打字会更新 liveContent；保存成功后 updateContentBaseline 执行 t.liveContent = content，用旧快照覆盖了用户的新输入。表现为：打字很快的用户按 Ctrl+S 后，那一瞬间敲下的字符凭空消失。

baseline 推进时不要回写 liveContent——仅更新 baseline = content 并重算 dirty = liveContent !== baseline；编辑器内容以 CodeMirror 为唯一事实源，不反向覆盖。（作者已在 TECHNICAL.md §8.2 列为 P1，本审查确认其真实性并补充了具体丢失路径。）
🔴 #3关闭窗口不触发未保存协商（数据丢失路径）frontend/src/titlebar.ts:62-64 / unsaved-guard.ts:38-46

自绘标题栏的关闭按钮直接调 Quit()，Wails v2.14 该路径不触发 beforeunload（titlebar.ts 注释自证），unsaved-guard 的拦截形同虚设。README 宣传「关闭未保存提示」，实际点 X = 静默丢弃所有未保存修改。

短期：关闭按钮改为先检查 tm.hasAnyDirty()，脏时弹 unsavedDialog 确认后再 Quit。长期：接 Wails OnBeforeClose 异步协商（作者已列为 P1-E 待办，与 #2 同属发版前必修）。
🟡 #5PushRecent 读-改-写非事务化（TOCTOU 竞态）app.go:249-259 / internal/config/config.go:40-45

Load() → PushRecent() → Save() 三步之间锁已释放，Store.mu 只保护单次调用。快速连续保存两个文件时存在丢更新窗口（前端 pushRecent(...).catch(warn) 是 fire-and-forget，恰好放大了触发概率）。后果限于最近文件列表错乱，不损坏文档。

在 config.Store 上加 Mutate(func(Config) Config) 方法，锁内完成读-改-写全序列；App.PushRecent 改调它。单一消费者场景下优先级不高，但修复成本仅约 20 行。
🟢 #11SaveFileAs 忽略 Abs 错误app.go:180

abs, _ := filepath.Abs(target) 吞掉错误，极端场景（路径含非法字符）返回值不可靠。影响极小。

失败时回退 abs = target，与 OpenFile 的处理方式对齐（app.go:99-103 有正确示范，两处行为应一致）。

UI 缺陷

🔴 #1预览区 H1–H3 样式全部失效（实测确认）frontend/src/style.css:652-660

CSS 写的是 .preview .md-h1 { font-size:1.8em; color:var(--md-h1); border-bottom:... }，但 marked 输出的是裸 <h1> 标签，不带任何 class（本审查沙箱实测 renderMarkdown("# 标题一") → <h1>标题一</h1>）。选择器永远不命中——预览区标题退化为浏览器默认样式，设计的字号层级、主题色、标题下划线全部丢失；而 h4–h6 反而用了标签选择器有样式。属于「设计了但从未生效」的静默失效。

把三行选择器改为标签形式：.preview h1 {...} .preview h2 {...} .preview h3 {...}（或用 marked renderer 注入 class）。一行修复，收益立竿见影；建议顺手加一个「渲染 # Hello 断言含 style 特征」的回归测试防再犯。
🟡 #8Callout 配色未随亮色主题变量化frontend/src/style.css:826-876

12 种 callout 的边框色/背景/图标色全部硬编码暗色系值（#79C0FF、rgba(121,192,255,.08) 等）。亮色米杏底上呈饱和度错配：蓝色系在浅底偏灰暗、rgba 背景近乎不可见，视觉层级弱于暗色主题。项目明明已有完整的 CSS 变量体系，此处是唯一成片的「逃逸区」。

为 callout 定义 --callout-note 等语义变量，暗/亮两套值放入 :root 与 [data-theme="light"] 块，与主色体系对齐。
🟢 #13CSS 死代码与不可达选择器frontend/src/style.css:521-545, 790-793

.editor / #editor 是旧 textarea 时代的遗留样式块（现用 .cm-host）；.wiki-link[data-broken="true"] 无任何代码路径设置 data-broken 属性，断链标红功能「设计了选择器、没写逻辑」。

删除两处死代码；data-broken 若是规划中的断链检测，在 main.ts 的 onWikiLinkClick 找不到目标时回写该属性即可点亮。

05安全模型审查

项目实现了 8 层纵深防御（TECHNICAL.md §4 与代码逐层核对一致），本审查重点验证了渲染管线的两条硬约束与占位符防伪设计：

Markdown 源文本
  → ① extractLatex（随机盐占位符）      ← latex.ts，防 marked 破坏公式
  → ② preprocessAll（双链/callout）      ← obsidian.ts
  → ③ marked.parse
  → ④ DOMPurify 严格白名单               ← preview.ts:45-58
  → ⑤ hardenLinks（DOM 级外链加固）      ← preview.ts:70-83
  → ⑥ restoreLatex（仅 >...< 文本节点）  ← 关键：不触碰属性上下文
  → ⑦ DOM 兜底 scrub                     ← preview.ts:124-135
  → ⑧ safeWritePath 写路径守卫            ← Go 侧 safepath.go
  • 顺序约束正确且有注释论证：公式先提取（防 a_i * b_j 被斜体破坏）、后还原（防 DOMPurify 剥离 KaTeX 的 style/MathML）——两处「为什么」都写进了代码注释
  • 占位符防伪双保险经得起推敲：每次随机盐 + 提取前剥除用户文本中的占位符形态（PH_LIKE_RE），即使攻击者伪造 LTMDPHLX...ZX 也无法把 KaTeX HTML 注入属性上下文；测试有 5 项专项覆盖（wiki-link 别名/img title 属性/盐唯一性等）
  • KaTeX trust:false + maxSize/maxExpand：禁 \href/\htmlClass 等注入命令，宏展开炸弹有测试；KaTeX 0.16.47 高于 CVE-2025-23207 的修复版本 0.16.21 ✓
  • hardenLinks 用 DOMParser 而非正则：覆盖单引号/跨行/属性含 > 的边界（F10 修复有注释溯源）
  • DOMPurify 配置审读无漏洞：ALLOWED_URI_REGEXP 白名单协议；style 属性对 KaTeX 的放行依赖「还原发生在清洗之后 + trust:false」，设计上是声明过的受控例外
🟡 #6依赖漏洞：esbuild 开发服务器任意请求读取（1 高危 + 1 中危）frontend/package.json:16（vite ^3.0.7）

npm audit 实测报 GHSA-67mh-4wv8-2f99：esbuild ≤0.24.2 开发服务器可被任意网站跨域读取响应。仅影响 wails dev / vite dev 开发场景（生产产物不含 dev server，Wails 打包的是静态 dist），不构成线上风险。但 vite 3 已停止维护两年余，后续升级路径越拖越陡。

升级 vite 至 5.x/6.x（devDependencies 变更不影响产物体积；需同步验证双入口 rollupOptions 与 katexWoff2Only 插件兼容性）；CI 加 npm audit --audit-level=high 门禁。作者已列为 P1，建议与 #4 一并处理。
🟡 #9图片插入的 Markdown 转义缺失frontend/src/main.ts:171-182

![${file.name}](${assetPath}) 直接拼接：文件名含 ) / ] / 空格会截断 markdown 结构；Windows 绝对路径的反斜杠在 markdown URL 中是转义字符（C:\Users → C:Users）；alt 文本含 [ 同理破坏。作者已列为 P2。

URL 侧做 encodeURI + 反斜杠→正斜杠替换（Obsidian 也用 /），alt 侧转义 [ ]；同时考虑改插相对路径（相对 .md 文件目录）而非绝对路径，笔记库整体搬迁时图片不失效。
🟢 #15Windows 保留设备名判定用最后一个点剥扩展名internal/fileio/safepath.go:48-49

CON.x.md 按最后一个点剥除得 CON.x（不拦截），但 Windows 对第一个点前的保留名同样可能解析为设备。极边缘场景（本地单用户应用、攻击面需要先突破前端）。

改用 strings.Index(base, ".") 取第一个点前段判定，覆盖多级扩展名形态。

🟡 #7build/ 与 build_darwin/ 双目录并存且内容漂移build/darwin/Info.dev.plist ↔ build_darwin/Info.dev.plist

实测两份 Info.dev.plist 内容不一致。Wails v2 标准读取 build/，build_darwin 是 macOS 构建遗留；真相源不清晰，macOS 产物可能用错配置。TECHNICAL.md 的目录树也只记载了 build_windows/ 未提 build_darwin/，文档同样失真。

合并到 build/darwin/ 单一真相源后删除 build_darwin/；或在文档中明确两者的角色分工。
🟡 #10wails.json 与构建脚本的依赖安装方式不一致wails.json:5 ↔ build-win11-x64.sh:57

脚本用 npm ci（严格按 lockfile，可复现），wails.json 的 frontend:install 是 npm install（可能更新 lockfile）。构建脚本声称「跨构建 exe SHA256 一致」，但走 wails build 内部安装路径时依赖版本可能漂移，破坏该承诺。

wails.json 的 frontend:install 改为 npm ci。
🟢 #17源码分发包含 .git 与 node_modules分发包整体

2.9MB 源码包中 .git 占 2.3MB，node_modules 亦被打入（含对 Windows 构建无意义的 darwin 二进制）。

发布源码用 git archive --format=zip -o LiteMD-src.zip HEAD，自动排除未跟踪内容；或打包含 .gitignore 规则过滤的 tar。

11结语

LiteMD 展示了「小而正确」的工程审美：原子写知道为什么 Sync、ReDoS 修复附实测毫秒数、体积优化逐项给数据、文档与代码互相校准、待办带根因与优先级。安全设计（8 层纵深 + 占位符盐防伪）在同类 Markdown 编辑器中属于第一梯队。

短板同样清晰：数据链路的「最后一公里」——保存竞态、关窗协商、标题样式静默失效，三者都是「设计意图存在、落地偏差一格」的缺陷，修复成本低但用户感知强。建议按 P0 清单在 0.2.1 收口，再启动依赖升级与 CI 建设。
