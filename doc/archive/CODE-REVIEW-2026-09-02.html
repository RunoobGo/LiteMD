P0-2CopyImageAsset 是一个"任意文件写入"原语
位置
app.go:363-373 → internal/fileio/fileio.go:135-181 → internal/fileio/safepath.go:50-65
证据
safepath.go 的 safeWritePath 只校验三件事：非空、绝对路径、Windows 保留设备名。没有根目录约束、没有扩展名白名单、没有大小上限。前端 file-ops.ts:47 直接透传路径。
影响
一旦预览区出现 XSS 绕过，或前端路径拼接出错，即可写入 ...\Start Menu\Programs\Startup\a.bat 或任意 .exe；MkdirAll(dir, 0o755)（fileio.go:156）还会顺手建目录。这是全项目危害等级最高的一条 —— 你在 safepath.go:11-17 的注释里已经意识到"会成为任意写入原语"，但守卫只做了一半。
修复
// fileio.go —— 加扩展名白名单 + 流式解码 + 大小上限
var imageWriteExts = map[string]bool{".png":true,".jpg":true,".jpeg":true,
  ".gif":true,".webp":true,".bmp":true,".ico":true,".avif":true}

func WriteBase64File(path, base64Data string) error {
    clean, err := safeWritePath(path)
    if err != nil { return err }
    if !imageWriteExts[strings.ToLower(filepath.Ext(clean))] {
        return fmt.Errorf("%w: not an image ext: %s", ErrUnsafePath, clean)
    }
    payload := base64Data
    if i := strings.LastIndex(payload, ","); i >= 0 && strings.HasPrefix(payload, "data:") {
        payload = payload[i+1:]
    }
    const maxImageBytes = 20 << 20
    src := io.LimitReader(base64.NewDecoder(base64.StdEncoding, strings.NewReader(payload)), maxImageBytes+1)
    data, err := io.ReadAll(src)          // 不再一次性 DecodeString 全量进内存
    if err != nil { return fmt.Errorf("decode base64: %w", err) }
    if len(data) > maxImageBytes { return errors.New("image too large (max 20MB)") }
    return writeAtomic(clean, data)        // 见 P0-3 的统一实现
}
更彻底的方案（💡）：Go 1.25 已提供 os.Root（os.OpenRoot）。给 CopyImageAsset / SaveFile / ResolveLocalPath / ReadLocalAsset 都加上"笔记库根目录"参数，用 os.Root 打开，可一次性消灭目录穿越、8.3 短名、UNC、符号链接与任意读写五类问题，比逐项打补丁更稳。
P0-3原子写不完整：每次保存把文件权限改成 0600，且 rename 后未 fsync 目录
位置
internal/fileio/fileio.go:103（CreateTemp）、:118-127（Sync + Rename）· internal/config/config.go:115-143（三份重复实现）
问题 A
os.CreateTemp 固定 0600，rename 后目标文件继承该模式。覆盖已有文件时原权限 / ACL 永久丢失：Windows 上备份与同步工具、同机其他用户会读不到笔记；Unix 上组权限被吞。用户会认为"LiteMD 把我的文件权限改坏了"。
问题 B
只 sync 了临时文件数据，没有 sync 父目录。掉电后 rename 的目录项可能未落盘，出现"旧文件已消失、新文件不存在"—— 恰好违背 fileio.go:88 注释里"防止崩溃导致原文件损坏"的设计目标。
修复
mode := fs.FileMode(0o644)
if st, err := os.Stat(path); err == nil { mode = st.Mode().Perm() }   // 保留原权限

tmp, _ := os.CreateTemp(dir, ".litemd-*.tmp")
...
if err := os.Chmod(tmp.Name(), mode); err != nil { _ = os.Remove(tmp.Name()); return err }
if err := os.Rename(tmpPath, path); err != nil {
    // Windows：目标被杀软/索引句柄占用时 Rename 会 ERROR_ACCESS_DENIED，加一次短退避重试
    return err
}
if d, err := os.Open(dir); err == nil {                                // 补目录 fsync
    if err := d.Sync(); err != nil { _ = d.Close(); return fmt.Errorf("dir sync: %w", err) }
    _ = d.Close()
}
另建议抽取 writeAtomic(dir, path string, mode fs.FileMode, r io.Reader) error 单一实现。现在 fileio.go:90、fileio.go:135、config.go:115 是三份几乎相同的临时文件逻辑，权限 / 目录 fsync / 重试三处 bug 各修一遍极易漏掉一处。
P0-4切换标签后按 Ctrl+Z，会把 A 文件的内容撤销进 B 文件
位置
frontend/src/editor.ts:150-158（setContent）· 注释在 :142-149
证据
setContent 只加了 Transaction.addToHistory.of(false) 标注，没有隔离 history 栈本身。该标注只让"本次切换"不进历史，A 文件此前的编辑记录仍留在栈里。
影响
切到 B 后用户按 Ctrl+Z（本意是撤销自己刚才在 B 里的输入），CM6 取栈顶 —— 那是 A 文件的最后一个变更 —— 对当前文档 B 做 invert 并应用 → B 的内容被 A 的片段污染 → 触发 syncLiveContent 标记 B 脏 → 用户一保存就把 A 的内容写进 B 文件。editor.ts:148 的注释声称已防住"跨文件数据污染"，实际只防住了一半。
修复
// editor.ts：按 tabId 缓存独立 EditorState，history 随状态一并隔离
private states = new Map<string, EditorState>();

private buildState(doc: string): EditorState {
  return EditorState.create({ doc, extensions: this.extensions });
}

setDoc(tabId: string, content: string) {
  let st = this.states.get(tabId);
  if (!st) { st = this.buildState(content); this.states.set(tabId, st); }
  this.view.setState(st);      // 切回时 view.setState(this.states.get(id)) 即可
}

P0-5保存无并发守卫；文件被外部程序改了会静默覆盖（diskMtime 只写不读）
位置
frontend/src/main.ts:884-900（handleSave）、:902-917（handleSaveAs）、frontend/src/tabs.ts:17/94/158
证据 A
grep -rn diskMtime frontend/src/ 只有 3 处命中：tabs.ts:17 声明、:94 写入、:158 写入 —— 全项目没有任何读取点。Go 侧 OpenFile 返回的 FilePayload.Modified（app.go:113）前端也从未消费。
证据 B
main.ts:893 与 :909 写入的是 Date.now() / 1000（本地时钟），不是磁盘真实 mtime。
影响
① 并发保存错序：无 in-flight 锁。快速连按两次 Ctrl+S，两次 saveFile 并发，落盘顺序不保证。若旧内容的那次后落盘，界面显示"✓ 已保存"但磁盘上是旧内容，用户关窗口即丢稿。 ② 外部修改静默覆盖：用户用别的编辑器 / 同步盘改了文件，LiteMD 下次保存直接盖掉，无任何冲突提示。
核实
关于 git 历史里 f170978"修复保存误报失败"：该修复只改了 mocks.ts（无头环境 window.prompt 抛异常冒泡成"另存为失败"）。真实桌面路径当时就是对的 —— saveFile 失败会 reject 进 catch，不会误标已保存。所以这条没坏，但也从没在真机上坏过；真正缺的是上面两条。
修复
const saving = new Set<string>();          // 保存串行化

async function handleSave(): Promise<boolean> {
  const a = tm.active;
  if (!a || saving.has(a.id)) return false;
  saving.add(a.id);
  try {
    if (!a.path) return await handleSaveAs();
    // 保存前比对磁盘 mtime，变了就提示
    const disk = await window.go.main.App.FileMtime(a.path);
    if (a.diskMtime && disk > a.diskMtime + 1) {
      if (!await confirmConflict(a.path)) return false;
    }
    const content = editor ? editor.getContent() : a.liveContent;
    await saveFile(a.path, content);
    tm.updateContentBaseline(a.id, content, a.path, await window.go.main.App.FileMtime(a.path));
    return true;
  } finally { saving.delete(a.id); }
}
Go 侧补一个 func (a *App) FileMtime(path string) (int64, error)；窗口重新获得焦点时也做一次全标签比对。
